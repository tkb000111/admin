# 01 - 架构解析：这个底座是怎么搭起来的

> 写给不懂代码的项目主人。这份文档所有结论都来自对项目源代码的逐一阅读，每个文件路径都是磁盘上真实存在的位置，可以直接打开对照。
>
> 阅读约定：技术名词第一次出现时，都会用一句话解释。文件路径写在反引号里（灰色代码样式），例如 `scaffold-system/pom.xml`，表示项目根目录下的这个文件。

## 〇、先看整体：一套系统，五个角色

这个项目跑起来之后，实际参与工作的是下面五个角色：

| 角色 | 是什么 | 在哪个文件夹 |
| --- | --- | --- |
| 网关（Gateway） | 大门保安。浏览器只跟它打交道，它把页面文件发给浏览器，把 `/api` 开头的请求转交给后端 | `gateway/server.mjs` |
| 前端（Vue） | 你在浏览器里看到的所有界面、按钮、表格 | `scaffold-vue/` |
| 后端（Spring Boot） | 真正干活的大脑：验证身份、判断权限、读写数据 | `scaffold-system/`（内含 5 个子模块，见下文） |
| MySQL 数据库 | 仓库。所有用户、角色、菜单、日志都存放在这里 | 建库脚本在 `scaffold-system/sql/` |
| Redis | 一块高速便签板。存放「登录令牌」和「验证码」这类临时的、需要快速读取的小数据 | 配置见 `scaffold-system/scaffold-admin/src/main/resources/application-dev.yml` |

请求的整体走向是：**浏览器 → 网关(:18090) → 后端(:18091) → 数据库 / Redis**（以 `./启动.sh` 整栈启动为准；桌面版则占 18080/18081，后端在 `scaffold-system/scaffold-admin/src/main/resources/application.yml` 第 8-10 行的默认端口是 18081，可被启动脚本覆盖）。后端自己不直接对外，统一由网关代理出去；开发模式（`./启动.sh 开发`）不走网关，前端(5173)直连开发后端(18085)。

## 一、后端五大模块：各管什么，谁依赖谁

后端代码按「Maven 模块」划分。Maven 模块——可以理解为后端代码的分房间管理：每个房间放一类职责的代码，房间之间的依赖关系写死在各自的 `pom.xml`（模块的"户口本"文件）里，谁要用谁、一目了然。

### 1.1 五个模块一览

| 模块 | 大白话职责 | 内容清单 | 户口本 |
| --- | --- | --- | --- |
| `scaffold-common` | **公共词表**。全后端共用的"标准信封"（统一返回结构）、"标准分页参数"和业务异常类，代码量最少但人人都要用 | 3 个领域类 + 1 个异常类 | `scaffold-system/scaffold-common/pom.xml` |
| `scaffold-framework` | **保安与礼仪部**。登录令牌（JWT）、权限校验、数据范围、操作日志、统一异常处理、请求追踪号，全部统一封装在这里。它不认识任何业务，只提供通用能力 | security / datascope / audit / handler / filter / config 六个包，共 17 个类 | `scaffold-system/scaffold-framework/pom.xml` |
| `scaffold-system` | **业务主力**。登录、用户/角色/菜单/部门/岗位/字典/参数管理、日志查询、驾驶舱统计都在这里。它依赖 framework 提供的通用能力，自己只写业务逻辑 | 4 个 Controller、6 个 Service、4 个 Mapper | `scaffold-system/scaffold-system/pom.xml` |
| `scaffold-generator` | **代码工厂**。把数据库里已有的表导进来，自动生成新模块的后端代码骨架，减少重复劳动 | 1 个 Controller + Service + Mapper | `scaffold-system/scaffold-generator/pom.xml` |
| `scaffold-admin` | **总装车间**。整个后端唯一的"启动器"：只有一个 main 启动类、一个健康检查接口、一套配置文件和数据库初始化工具。它把上面四个模块全部拼装到一起运行 | 启动类、HealthController、DbInit、application 配置 | `scaffold-system/scaffold-admin/pom.xml` |

### 1.2 依赖关系（谁离不开谁）

```
scaffold-admin（总装：依赖下面所有模块，是唯一能启动的模块）
   ├── scaffold-generator ──┐
   ├── scaffold-system ──────┤── 都依赖 scaffold-framework
   └── scaffold-framework ───┘
            └── scaffold-common（最底层，人人都要用）
```

- `scaffold-common` 依赖最干净：只有参数校验（validation）和测试工具，见 `scaffold-system/scaffold-common/pom.xml` 第 16-26 行。
- `scaffold-framework` 在 common 之上引入了 Web、安全（security）、切面（AOP——一种"给所有符合条件的代码自动套一层统一动作"的机制）、Redis 和 JWT（JSON Web Token——登录后发的一张加密通行证）库，见 `scaffold-system/scaffold-framework/pom.xml` 第 16-56 行。
- `scaffold-system` 在 framework 之上引入了 MyBatis-Plus（把 Java 代码和 SQL 数据库查询对应起来的框架）和 MySQL 驱动，见 `scaffold-system/scaffold-system/pom.xml` 第 16-30 行。
- `scaffold-admin` 把所有模块集中装配，并声明"只有我这里能执行启动"，见 `scaffold-system/scaffold-admin/pom.xml` 第 17-19 行的注释与配置。

### 1.3 后端代码放在哪个"楼层"：包结构

| 模块 | 关键包（package） | 里面放什么 |
| --- | --- | --- |
| common | `com.scaffold.common.domain` | `R`（统一返回信封）、`PageQuery`（分页请求）、`PageResult`（分页结果） |
| common | `com.scaffold.common.exception` | `BusinessException`（业务异常——"这是业务上不允许的情况，请提示用户"） |
| framework | `com.scaffold.framework.security` | JWT 签发与解析、令牌存取、验证码、权限注解与校验切面、401/403 统一回复 |
| framework | `com.scaffold.framework.datascope` | 数据权限（不同人只能看自己该看的数据）的注解与切面 |
| framework | `com.scaffold.framework.audit` | 操作日志注解与记录切面 |
| framework | `com.scaffold.framework.handler` | 全局异常处理（任何报错都变成统一的回复格式） |
| framework | `com.scaffold.framework.filter` | 请求追踪号（traceId）过滤器 |
| framework | `com.scaffold.framework.config` | Spring Security 安全总配置 |
| system | `com.scaffold.system.controller` | 前台接待员：接收前端请求并返回结果 |
| system | `com.scaffold.system.service` | 业务员：真正的业务规则在这里 |
| system | `com.scaffold.system.mapper` | 仓库管理员：把业务要求翻译成 SQL 去查数据库 |
| system | `com.scaffold.system.domain` | 数据的"格式模板"（DTO 请求对象 / VO 返回对象） |
| generator | `com.scaffold.generator.*` | 代码生成（controller / service / mapper） |
| admin | `com.scaffold.admin` | 启动类 + 健康检查 + 数据库初始化工具 |

> 注意一个容易误解的点：**这个项目没有 Mapper XML 文件**。所有 SQL 都以注解形式直接写在 Mapper 接口的 Java 文件里（用 `@Select`、`@Insert`、`@Update` 注解 + 三引号文本块），例如 `scaffold-system/scaffold-system/src/main/java/com/scaffold/system/mapper/AuthMapper.java` 第 16-23 行。想找 SQL，直接打开 Mapper 接口文件看即可。

## 二、统一公共能力清单：底座替你做好的事

这些能力全部集中封装，业务代码"声明一下"就能用，不许各页面自己造。这是本脚手架「统一底座」原则的核心。

| 能力 | 是什么（大白话） | 定义在哪个文件 | 业务代码怎么用上它 |
| --- | --- | --- | --- |
| 统一返回结构 | 所有接口都返回同一个"信封"：`code` 状态码（200 成功）、`message` 提示语、`data` 业务数据、`traceId` 追踪号 | `scaffold-system/scaffold-common/src/main/java/com/scaffold/common/domain/R.java` 第 13-24 行 | Controller 里一律 `return R.success(数据)`，如 `scaffold-system/scaffold-system/src/main/java/com/scaffold/system/controller/AuthController.java` 第 44 行 |
| 统一异常处理 | 任何地方出错了，都由一个"总收发室"把错误翻译成统一信封格式返回，前端永远拿到结构一致的报错 | `scaffold-system/scaffold-framework/src/main/java/com/scaffold/framework/handler/GlobalExceptionHandler.java` 第 23-71 行 | 业务代码只需 `throw new BusinessException("提示语")`，异常类在 `scaffold-system/scaffold-common/src/main/java/com/scaffold/common/exception/BusinessException.java` |
| 统一参数校验 | 请求内容不合格（比如必填项为空）自动拦下并返回 400 | 校验规则来自 common 的 validation 依赖；失败由 GlobalExceptionHandler 第 28-35 行兜住 | 请求对象上加校验注解，Controller 方法参数前加 `@Valid`（见 AuthController 第 40 行） |
| 统一权限校验 | 接口上贴一个"权限标签"，用户没有对应权限就自动拒绝（返回 403） | 注解：`scaffold-system/scaffold-framework/src/main/java/com/scaffold/framework/security/RequiresPermission.java`；执行校验的切面：同目录 `PermissionAspect.java` 第 21-29 行 | Controller 方法上加 `@RequiresPermission("system:user:list")`，见 `scaffold-system/scaffold-system/src/main/java/com/scaffold/system/controller/SystemManagementController.java` 第 47-49 行 |
| 统一数据范围（数据权限） | 更细一层的权限：同接口，不同人看到的**数据条数**不同（比如部门主管只看本部门） | 注解：`scaffold-system/scaffold-framework/src/main/java/com/scaffold/framework/datascope/DataScope.java`；切面：同目录 `DataScopeAspect.java` 第 20-30 行；范围计算规则由业务侧实现：`scaffold-system/scaffold-system/src/main/java/com/scaffold/system/service/SystemDataScopeResolver.java` 第 22-49 行 | Service 方法上加 `@DataScope`，再把 `DataScopeContext.current()` 作为参数传给 Mapper，SQL 里据此拼条件（见 `scaffold-system/scaffold-system/src/main/java/com/scaffold/system/service/SystemManagementService.java` 第 75-81 行） |
| 统一操作日志 | 给接口贴"记录标签"，谁在什么时候对什么模块做了什么、耗时多少、成功失败，自动写入 `sys_oper_log` 表 | 注解：`scaffold-system/scaffold-framework/src/main/java/com/scaffold/framework/audit/OperLog.java`；切面：同目录 `OperationLogAspect.java` 第 33-60 行；落库实现：`scaffold-system/scaffold-system/src/main/java/com/scaffold/system/service/JdbcOperationLogRecorder.java` 第 18-37 行 | Controller 写操作上加 `@OperLog(module = "用户管理", action = "新增")`（SystemManagementController 第 78 行）。密码、令牌等敏感字段会自动打码成 `******`（OperationLogAspect 第 79-102 行） |
| 统一分页 | 前端传"第几页、每页几条"，后端按统一规则处理，每页上限 100 条防刷 | `scaffold-system/scaffold-common/src/main/java/com/scaffold/common/domain/PageQuery.java`（第 13-33 行含默认值与上限）；返回用 `PageResult.java` 第 13-17 行 | Controller 方法直接声明 `PageQuery query` 参数；Service 里用 `pageOf()` 换算偏移量（SystemManagementService 第 692-697 行），Mapper 里 `LIMIT #{offset}, #{pageSize}` |
| 统一追踪号 | 每个请求分配一个唯一编号 traceId，出问题靠它把日志串起来 | `scaffold-system/scaffold-framework/src/main/java/com/scaffold/framework/filter/TraceIdFilter.java` 第 23-37 行 | 自动生效；R.java 第 19 行把追踪号塞进每个响应 |
| 统一认证（登录态） | 未登录或登录过期一律返回统一 401；无权访问返回统一 403 | 401 入口：`scaffold-system/scaffold-framework/src/main/java/com/scaffold/framework/security/RestAuthenticationEntryPoint.java`；403 出口：同目录 `RestAccessDeniedHandler.java`；哪些地址要登录：`scaffold-system/scaffold-framework/src/main/java/com/scaffold/framework/config/SecurityConfig.java` 第 40-49 行 | 自动生效；业务代码无需处理 |

## 三、登录与权限完整链路：从点下"登录"按钮到看见页面

**先认识两位主角：**
- **token（令牌）**：登录成功后后端发的一张"通行证"，之后每次请求都要出示。
- **Redis**：内存数据库，速度极快，这里用来存放通行证的有效性记录和验证码。

### 第 1 步：打开登录页，先拿验证码

| 环节 | 做什么 | 文件与职责 |
| --- | --- | --- |
| 前端要验证码 | 登录页加载时调 `/api/auth/captcha` | `scaffold-vue/src/views/Login.vue` 第 99-111 行发起请求；`scaffold-vue/src/api/auth.ts` 第 54 行定义该接口 |
| 后端生成验证码 | 随机 4 位字符，存入 Redis（键 `captcha:uuid`，5 分钟过期），并把 uuid 和字符一起返回 | `scaffold-system/scaffold-framework/src/main/java/com/scaffold/framework/security/CaptchaService.java` 第 25-36 行 |

### 第 2 步：点登录，后端三道关

| 环节 | 做什么 | 文件与职责 |
| --- | --- | --- |
| 前端提交 | 把账号、密码、验证码、uuid 打包 POST 到 `/api/auth/login` | `scaffold-vue/src/views/Login.vue` 第 124 行；请求格式定义在 `scaffold-vue/src/api/auth.ts` 第 52-56 行 |
| 第一关：验证码校验 | 拿 uuid 去 Redis 对答案，对完即作废（防重复使用） | `scaffold-system/scaffold-system/src/main/java/com/scaffold/system/controller/AuthController.java` 第 39-45 行 + `CaptchaService.java` 第 38-45 行 |
| 第二关：账号密码校验 | 到数据库找账号、用 BCrypt（密码加密算法，只比对不还原）核对密码；查不到或密码错、账号停用 → 记一条失败登录日志并拒绝 | `scaffold-system/scaffold-system/src/main/java/com/scaffold/system/service/AuthService.java` 第 42-57 行；查库语句在 `scaffold-system/scaffold-system/src/main/java/com/scaffold/system/mapper/AuthMapper.java` 第 16-23 行 |
| 第三关：发通行证 | 生成 JWT 令牌，同时把「令牌 → 用户名」写进 Redis（有效期 7200 秒 = 2 小时，见 `application.yml` 第 16 行），最后记成功日志、更新最近登录时间 | JWT 签发：`scaffold-system/scaffold-framework/src/main/java/com/scaffold/framework/security/JwtService.java` 第 35-45 行；写入 Redis：同目录 `TokenStore.java` 第 20-22 行 |

### 第 3 步：前端保存通行证，并取回"我是谁、我能看什么"

| 环节 | 做什么 | 文件与职责 |
| --- | --- | --- |
| 存令牌 | 令牌、用户信息、过期时间存入浏览器本地存储；勾了"记住我"存 localStorage（长期），否则 sessionStorage（关浏览器就没） | `scaffold-vue/src/api/session.ts` 第 29-45 行 |
| 拿身份与权限码 | 调 `GET /api/auth/me`：返回用户名、部门、角色编码、**权限码列表**（如 `system:user:list`）。超管直接放行全部权限码 | 前端：`scaffold-vue/src/composables/auth.ts` 第 201-210 行、第 216-234 行；后端：`AuthService.java` 第 68-80 行；权限码查库 SQL：`AuthMapper.java` 第 34-46 行 |
| 拿菜单 | 调 `GET /api/auth/routes`：按角色从 `sys_menu` 表查出的菜单树。超管看全部菜单，普通角色只看被授权的 | 前端：`auth.ts` 第 182-198 行 `loadRoutes()`；后端：`AuthService.java` 第 82-89 行；菜单 SQL：`AuthMapper.java` 第 48-79 行 |

### 第 4 步：前端动态注册页面

| 环节 | 做什么 | 文件与职责 |
| --- | --- | --- |
| 页面登记表 | 前端维护一张「后端组件路径 → 前端页面文件 + 取数方式」的唯一对照表。后端菜单说"打开 system/user/index"，前端就按表找到对应页面 | `scaffold-vue/src/composables/auth.ts` 第 64-128 行（`PAGE_MAP`） |
| 动态注册路由 | 路由守卫（页面跳转前的检查员）发现已登录但菜单没加载，就先加载菜单，再把每个菜单注册成可访问的地址 | `scaffold-vue/src/router/index.ts` 第 46-91 行（`ensureRoutes` 与 `beforeEach`） |
| 守门规则 | 没登录 → 踢回登录页；接口返回 401 → 清空登录态回登录页 | `scaffold-vue/src/router/index.ts` 第 69-91 行、第 100-108 行 |

### 第 5 步：页面上的按钮按权限显示

| 环节 | 做什么 | 文件与职责 |
| --- | --- | --- |
| 权限码全院共享 | 把 `/auth/me` 拿到的权限码放进一个全局响应式集合，界面随时可查 | `scaffold-vue/src/directives/permission.ts` 第 5-17 行 |
| 两种用法 | `PermissionButton` 组件：没权限就**不渲染**按钮（而非置灰）；`v-permission` 指令：控制任意元素的显隐 | `scaffold-vue/src/components/business/PermissionButton.vue` 第 24-29 行；`scaffold-vue/src/directives/permission.ts` 第 19-33 行 |

### 第 6 步：越权调接口？后端切面拒绝

前端隐藏按钮只是"不给你看"，真正的防线在后端：如果有人绕过界面直接调接口（比如用工具发请求），后端会再查一次数据库核对该用户是否真有这个权限码，没有就抛 403。

- 核对逻辑：`scaffold-system/scaffold-system/src/main/java/com/scaffold/system/service/SystemPermissionResolver.java` 第 19-28 行（超管直接通过；普通用户查「角色→菜单→权限码」三表关联）。
- 拦截动作：`scaffold-system/scaffold-framework/src/main/java/com/scaffold/framework/security/PermissionAspect.java` 第 21-29 行（无权抛出拒绝访问异常）。
- 统一回 403：`GlobalExceptionHandler.java` 第 37-40 行 + `RestAccessDeniedHandler.java` 第 26-32 行。
- 每次请求都会先验通行证：后端从请求头取出令牌 → 验签 → 再去 Redis 确认这张证没被注销，两关都过才放行（`JwtAuthenticationFilter.java` 第 27-43 行）。**这就是令牌要存 Redis 的原因：注销/被顶下线时，删掉 Redis 里那条记录，这张证立刻作废。**

## 四、一次典型请求的完整流转：以"查询用户列表"为例

假设管理员在用户管理页打开列表，一次请求的完整旅程如下（共 9 站）：

| 站 | 发生什么 | 依据文件 |
| --- | --- | --- |
| 1 | 页面外壳按登记表里 `system/user/index` 的取数配置发起 `GET /api/system/users?pageNum=1&pageSize=10`，自动带上 `Authorization: Bearer 令牌` 请求头 | `scaffold-vue/src/composables/auth.ts` 第 68-73 行；发请求并自动加令牌：`scaffold-vue/src/api/http.ts` 第 50-58 行 |
| 2 | 网关把 `/api` 请求原样转发给后端内部端口（`./启动.sh` 整栈为 18091，经 `BACKEND_PORT` 环境变量传入；`application.yml` 默认 18081） | `gateway/server.mjs` 第 38-51 行（转发调用在第 90 行） |
| 3 | 追踪号过滤器给请求发一个 traceId，全程日志可追踪 | `scaffold-system/scaffold-framework/src/main/java/com/scaffold/framework/filter/TraceIdFilter.java` |
| 4 | 令牌过滤器验签 JWT + 查 Redis 确认有效，把"当前用户是谁"放进安全上下文 | `scaffold-system/scaffold-framework/src/main/java/com/scaffold/framework/security/JwtAuthenticationFilter.java` 第 27-43 行 |

## 五、新增一个业务页面要经过的完整环节（8 步）

以现有的**岗位管理**（最简单的标准增删改查模块）为参照物。假设你要新增一个"客户管理"。

| 步骤 | 做什么 | 参照物（岗位管理对应的真实文件） |
| --- | --- | --- |
| 1. 建表 | 在数据库新建业务表（如 `biz_customer`），**必须带四个审计字段**：`create_by` 创建人、`update_by` 更新人、`create_time` 创建时间、`update_time` 更新时间；软删除（数据不真删、只打个"已删除"标记，可恢复可审计）再加 `deleted` 字段。建表 SQL 放进 `scaffold-system/sql/`，命名为 `V3__xxx.sql`（版本号递增，`DbInit` 工具会按序执行） | 建表范例：`scaffold-system/sql/V1__init_schema.sql` 第 21-35 行（sys_post 表，四字段在第 29-32 行）；执行工具：`scaffold-system/scaffold-admin/src/main/java/com/scaffold/admin/util/DbInit.java` 第 44-59 行 |
| 2. Mapper | 新建 Mapper 接口，用 `@Select`/`@Insert`/`@Update` 注解写 SQL：列表（COUNT + LIMIT 两段）、新增、修改、删除 | `scaffold-system/scaffold-system/src/main/java/com/scaffold/system/mapper/SystemManagementMapper.java` 第 220-254 行（岗位的计数与列表）、第 448-471 行（岗位增改删） |
| 3. Service | 写业务规则：参数检查、重名校验、组装返回；需要数据权限就加 `@DataScope`；分页用 `pageOf()` | `SystemManagementService.java` 第 186-190 行附近（岗位列表）、第 318 行附近（岗位新增的重名与默认值处理） |
| 4. Controller | 暴露 REST 接口（REST——前后端约定的"动词+名词"式接口风格：GET 查、POST 增、PUT 改、DELETE 删）；每个接口贴 `@RequiresPermission("biz:customer:list")` 等权限码；写操作再加 `@OperLog` | `SystemManagementController.java` 第 258-298 行（岗位的全部接口） |
| 5. 前端 api | 在 `scaffold-vue/src/api/` 下新增接口定义文件（或在现有文件里加一组），统一走 `httpClient` | `scaffold-vue/src/api/system.ts`（系统模块接口都集中在这里）；底层封装 `scaffold-vue/src/api/http.ts` |
| 6. 页面 + PAGE_MAP 登记 | 新建页面组件（优先复用 ListPage / DataTable / SearchForm / FormDialog / PermissionButton 等公共组件），然后在登记表 `PAGE_MAP` 加一条「组件路径 → 页面 + 取数 + 导出」 | `scaffold-vue/src/composables/auth.ts` 第 94-99 行（岗位页的登记写法） |
| 7. 菜单 SQL | 往 `sys_menu` 表插一条 `menu` 类型菜单（含 path、component、权限码）+ 若干 `btn` 类型按钮权限；再执行一条新版本 SQL（如 `V4__xxx.sql`） | 菜单种子范例：`scaffold-system/sql/V2__seed_data.sql` 第 67-70 行（岗位菜单 105）+ 第 68-70 行（按钮 1051-1053） |
| 8. 角色授权 | 登录后台 → 角色管理 → 给需要的角色勾选新菜单；超管无需授权自动可见 | 授权的存储与读取：`sys_role_menu` 表（`V1__init_schema.sql` 第 109-113 行）；读取 SQL：`AuthMapper.java` 第 48-61 行 |

> 做完这 8 步，新页面就会出现在侧边栏、按钮按权限显隐、列表自动具备查询/重置/分页/导出，后端也自动获得权限校验、数据范围、操作日志、统一异常四大保障。

**代码生成器可以替你走 1~4 步的一半力气**：在"系统工具 → 代码生成"页导入刚才建的表，配置字段后可一键生成 Controller/Service/Mapper 代码骨架（生成器只读表结构生成代码文件，不直接动你的业务数据）。入口：`scaffold-system/scaffold-generator/src/main/java/com/scaffold/generator/controller/GeneratorController.java`；配置存在 `gen_table` / `gen_table_column` 两张表（`V1__init_schema.sql` 第 218-252 行）。

## 六、数据库表清单

数据库 `scaffold_system` 共 16 张表，全部定义在 `scaffold-system/sql/V1__init_schema.sql`，示例数据在 `scaffold-system/sql/V2__seed_data.sql`。

| 表名 | 存什么（大白话） | 备注 |
| --- | --- | --- |
| `sys_user` | 用户账号：谁能用这个系统 | 密码只存加密后的密文；唯一键 username；软删除 `deleted`；带最近登录时间 |
| `sys_role` | 角色（岗位身份，如"超级管理员"）：决定权限集合 | `data_scope` 字段决定数据权限范围；`builtin=1` 为内置角色不可删改 |
| `sys_menu` | 菜单与按钮：侧边栏结构 + 每个操作的权限码 | `menu_type` 分目录 dir / 菜单 menu / 按钮 btn；**此表无 deleted 字段，删除为物理删除（数据直接从数据库消失，不像软删除那样可恢复）** |
| `sys_dept` | 部门树 | `ancestors` 存祖级路径，"查本部门及以下"靠它 + FIND_IN_SET |
| `sys_post` | 岗位（职务，如"架构师"），与角色是两回事 | 唯一键 post_code |
| `sys_user_role` | 用户 ↔ 角色的关联（谁拥有哪个身份） | 中间表，无审计字段 |
| `sys_user_post` | 用户 ↔ 岗位关联 | 中间表，无审计字段 |
| `sys_role_menu` | 角色 ↔ 菜单/按钮关联（角色被授予哪些权限） | 中间表，无审计字段 |
| `sys_role_dept` | 角色 ↔ 部门关联（数据权限选"自定义"时生效） | 中间表，无审计字段 |
| `sys_dict_type` | 字典类型（下拉选项的"类目"，如"用户性别"） | 唯一键 dict_type |
| `sys_dict_data` | 字典数据（类目下的选项，如"男/女/未知"） | `tone` 是给前端标签的颜色标记 |
| `sys_config` | 系统参数（键值对，如"新账号初始密码"） | `builtin=1` 为内置参数，接口层禁止删除 |
| `sys_oper_log` | 操作日志：谁对什么模块做了什么 | 日志表，无审计字段（本身即审计）；支持按条删与清空 |
| `sys_login_log` | 登录日志：谁何时登录成功/失败 | 预留了 ip/浏览器/系统字段（`V1` 第 191-195 行），**当前代码未写入** |
| `sys_file` | 文件信息表（预留） | 目前后端没有上传功能使用它 |
| `gen_table` / `gen_table_column` | 代码生成器的表配置与字段配置 | 生成器专用 |

**四审计字段约定**：`sys_user`、`sys_role`、`sys_menu`、`sys_dept`、`sys_post`、`sys_dict_type`、`sys_dict_data`、`sys_config`、`sys_file`、`gen_table` 都带 `create_by / update_by / create_time / update_time`（见各建表语句，以 `V1__init_schema.sql` 第 12-15 行为模板）；`*_log` 日志表、`*_role` 等关联中间表按约定豁免。新增业务表必须沿用此约定。

**默认账号与角色**（`V2__seed_data.sql` 第 28-44 行）：预置 6 个角色（super_admin 全部数据权限、sys_admin 本部门及以下、biz_admin 本部门、developer 仅本人、auditor 自定义、guest 停用）和 3 个演示账号 `admin / chensy / wumin`，admin 绑定超级管理员角色且拥有全部菜单（第 88-89 行）。

## 七、代码生成模块（一句话版）

`scaffold-generator` 是"半自动流水线"：从数据库导入一张已有表 → 配置每个字段在列表/表单/查询里怎么出现 → 预览并生成后端三件套（Controller/Service/Mapper）代码、可打包 zip 下载，由开发者人工放入工程再微调。它有自己独立的权限码 `tool:gen:list`，所有接口在 `scaffold-system/scaffold-generator/src/main/java/com/scaffold/generator/controller/GeneratorController.java`。

## 附：这套架构的"安全防线"速查

| 防线 | 拦什么 | 实现位置 |
| --- | --- | --- |
| 网关 | 统一入口，后端不直接暴露 | `gateway/server.mjs` |
| 令牌过滤 | 没有有效令牌进不了任何 `/api/**` | `JwtAuthenticationFilter.java` + `SecurityConfig.java` 第 40-49 行 |
| 权限切面 | 有令牌但没权限码 → 403 | `PermissionAspect.java` |
| 数据范围切面 | 有权限码但越权看别人的数据 → SQL 条件过滤 | `DataScopeAspect.java` + `SystemDataScopeResolver.java` |
| 操作日志切面 | 干了什么都留痕，敏感字段自动打码 | `OperationLogAspect.java` |
| 统一异常 | 报错不泄露堆栈细节，统一文案 | `GlobalExceptionHandler.java` |
| Redis 注销 | 退出登录/令牌过期立即失效 | `TokenStore.java` 第 28-30 行 |
