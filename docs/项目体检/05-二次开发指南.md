# 05 · 二次开发指南：在底座上长出你的业务

> 读者：不懂代码的项目主人，以及替你干活的开发者。本篇是「项目体检」系列的实操篇：把体检结论翻译成开发守则，再把「新增一个业务模块」的全流程一步步写明。
> 读前先看：01-架构解析（后端怎么搭、一个请求怎么流转、新增页面的 8 步概览）和 02-界面布局框架（界面由哪些公共组件拼成）。本文引用的路径与行号均已与磁盘真实文件核对。

## 二、动手前必读的体检结论

> 以下 5 条源自 03-问题与风险清单的结论口径（并与 04-性能专项、PROJECT_MAP.md 的对应记录交叉核对）。它们不影响「能不能开发」，但直接影响「开发出来的业务安不安全、快不快」。

| # | 问题 | 大白话 | 为什么开发业务前要心里有数 |
| --- | --- | --- | --- |
| 1 | 验证码明文返回（安全演示缺陷） | 登录页的验证码字符直接随接口返回给浏览器 | 演示阶段无妨；「热铁盒」若对真实用户开放，机器人脚本可以自动读取验证码撞库。上线前必须更换方案，别把演示级安全当成品 |
| 2 | 数据权限默认「全部可见」 | 数据权限是「选装件」：业务接口不显式加 @DataScope 注解、SQL 不拼范围条件，就是人人可见整张表 | 新业务每个列表/导出都要自查一遍「该不该限定范围」，漏接一个就是越权看别人数据的口子 |
| 3 | 权限校验无缓存 | 每个受权限保护的请求都实时查库 2-3 次核对身份 | 功能正确但开销固定存在；新业务一律走 @RequiresPermission 统一入口、别自建权限判断，将来加缓存只需改 SystemPermissionResolver 一处 |
| 4 | 操作日志同步写 | 每个增删改操作都「当场写完日志才返回」 | 人多后每个操作都被拖慢一点；新业务照常贴 @OperLog 即可，但要知道日志表会持续增长，别在业务代码里再手写日志 |
| 5 | sys_user_role 缺 role_id 索引 | 用户-角色对照表按「角色」方向查时只能整表逐行翻 | 新业务建关联表必须两个方向都建索引，别重蹈覆辙 |

## 三、现成可复用的能力清单

> 复用原则（AGENTS.md）：已有组件能满足就直接复用；多个页面要用的能力先沉淀成公共件；只有单场景独有的逻辑才写在业务里。

### 3.1 后端公共能力（详见 01 文档第二节）

| 能力 | 干什么（大白话） | 在哪 | 新业务怎么用 |
| --- | --- | --- | --- |
| 统一返回结构 | 所有接口返回同一个「信封」：code 状态码 / message 提示 / data 数据 / traceId 追踪号 | `scaffold-system/scaffold-common/src/main/java/com/scaffold/common/domain/R.java` | Controller 一律 `return R.success(数据)` |
| 统一异常处理 | 任何报错都由「总收发室」翻译成统一格式，前端拿到的报错永远长一样 | `scaffold-system/scaffold-framework/src/main/java/com/scaffold/framework/handler/GlobalExceptionHandler.java` | 业务里只管 `throw new BusinessException("提示语")`（异常类在 scaffold-common 的 exception 包） |
| 统一参数校验 | 必填项为空、格式不对自动拦下并返回 400 | 校验依赖在 scaffold-common；拦截由 GlobalExceptionHandler 兜底 | 请求对象字段上加校验注解，Controller 参数前加 `@Valid` |
| 统一权限注解 | 接口贴「权限标签」，没权限自动拒绝（403） | 注解 `scaffold-system/scaffold-framework/src/main/java/com/scaffold/framework/security/RequiresPermission.java`；校验切面同目录 `PermissionAspect.java` | Controller 方法上加 `@RequiresPermission("biz:customer:list")` |
| 数据范围注解 | 同接口不同人看到的**数据条数**不同（全部 / 本部门及以下 / 本部门 / 仅本人 / 自选） | 注解 `scaffold-framework/.../datascope/DataScope.java`；切面 `DataScopeAspect.java`；范围计算 `scaffold-system/.../service/SystemDataScopeResolver.java` | Service 方法加 `@DataScope`，取 `DataScopeContext.current()` 传给 Mapper、在 SQL 里拼条件（标准写法见 `SystemManagementService.java` 第 75-81 行） |
| 操作日志注解 | 谁在什么时候对什么模块做了什么，自动入库，敏感字段自动打码 | 注解 `scaffold-framework/.../audit/OperLog.java`；切面 `OperationLogAspect.java` | Controller 写操作上加 `@OperLog(module = "客户管理", action = "新增")` |
| 统一分页 | 前端传「第几页、每页几条」，后端按统一规则处理，每页上限 100 条防刷 | 入参 `scaffold-common/.../domain/PageQuery.java`；出参 `PageResult.java` | Controller 声明 `PageQuery` 参数；Service 用 `pageOf()` 换算；Mapper 里 `LIMIT #{offset}, #{pageSize}` |
| 追踪号与登录态 | 每个请求自动带追踪号；未登录统一 401、无权统一 403 | `scaffold-framework/.../filter/TraceIdFilter.java`、`security/RestAuthenticationEntryPoint.java`、`RestAccessDeniedHandler.java` | 自动生效，业务代码不用管 |
| 代码生成 | 导入数据库已有表，生成后端三件套（Controller/Service/Mapper）骨架并可下载 ZIP | `scaffold-system/scaffold-generator/src/main/java/com/scaffold/generator/controller/GeneratorController.java`；页面在「系统工具 → 代码生成」 | 用它省第 2-4 步的一半力气；生成的是骨架，业务逻辑仍需人工补齐，且不会自动写入工程 |

## 四、新增一个业务模块的完整步骤（虚构示例：客户管理）

> 假设「热铁盒」需要一个客户管理：记录客户名称、联系电话、等级、负责人，并按数据范围隔离。以下每步都给参照文件，照抄结构、替换字段即可。

### 第 1 步：设计表

- 表名 `biz_customer`（业务表建议 `biz_` 前缀），字段：`id` 主键、`customer_name` 客户名称、`phone` 联系电话、`level` 客户等级（存字典值）、`owner_user_id` 负责人用户 ID、`remark` 备注、`deleted` 软删除标记，**再加四个审计字段：`create_by` 创建人、`update_by` 更新人、`create_time` 创建时间、`update_time` 更新时间**（项目强制约定，见 AGENTS.md「数据库」与 README「新业务模块」第 1 条）。
- 索引按查询条件建：`customer_name` 唯一索引（防重名）、`owner_user_id` 普通索引（按负责人查 + 数据范围过滤都要用）。
- **建表 SQL 放哪**：`scaffold-system/sql/` 目录，版本号顺延命名，如 `V3__biz_customer.sql`（DbInit 工具按版本号顺序执行，见 `scaffold-system/scaffold-admin/src/main/java/com/scaffold/admin/util/DbInit.java`）。
- 建表范例：`scaffold-system/sql/V1__init_schema.sql` 第 21-35 行（sys_post 表，四审计字段在第 29-32 行）。

### 第 2 步：后端 Mapper（仓库管理员：把业务要求翻译成 SQL）

- 新建 `CustomerMapper.java` 接口（放 `scaffold-system/scaffold-system/src/main/java/com/scaffold/system/mapper/`，或按业务分包），SQL 用 `@Select`/`@Insert`/`@Update` 注解直接写在接口方法上（本项目没有 XML 映射文件）。
- 必须写：列表 **COUNT 一条 + LIMIT 取数一条**（数据库级分页）、新增、修改、删除；数据范围条件（`DataScopeCriteria`）显式拼进 WHERE。
- 参照：`scaffold-system/scaffold-system/src/main/java/com/scaffold/system/mapper/SystemManagementMapper.java` 第 219-253 行（岗位的计数与列表）、第 448-471 行（岗位增改删）。

### 第 3 步：后端 Service（业务员：真正的业务规则）

- 新建 `CustomerService.java`：重名校验、默认值处理、组装返回；需要数据权限就在方法上加 `@DataScope` 并取 `DataScopeContext.current()` 传给 Mapper；分页用 `pageOf()` 换算。
- 参照：`scaffold-system/scaffold-system/src/main/java/com/scaffold/system/service/SystemManagementService.java` 第 75-81 行（@DataScope 标准写法）、第 187 行（岗位列表）、第 318 行（岗位新增的重名与默认值处理）。

### 第 4 步：后端 Controller（前台接待员：接收请求并返回）

- 新建 `CustomerController.java`，按 REST 风格（前后端约定的「动词+名词」接口风格：GET 查 / POST 增 / PUT 改 / DELETE 删）暴露接口；每个接口贴 `@RequiresPermission("biz:customer:list|add|edit|remove")`，写操作再加 `@OperLog(module = "客户管理", action = "...")`；返回一律 `R.success(...)`。
- 参照：`scaffold-system/scaffold-system/src/main/java/com/scaffold/system/controller/SystemManagementController.java` 第 258-298 行（岗位的全部接口）。

### 第 5 步：前端 api 接入

- 在 `scaffold-vue/src/api/` 下新建 `customer.ts`（或并入现有文件），定义 list / create / update / remove / export 等函数，统一走 `scaffold-vue/src/api/http.ts` 的 httpClient。
- 参照：`scaffold-vue/src/api/system.ts`（系统模块接口都集中在这里）。

### 第 6 步：前端页面 + PAGE_MAP 登记（关键一步）

- 新建页面 `scaffold-vue/src/views/biz/Customers.vue`：套 ListPage 骨架，只填业务字段（列定义、查询字段、表单字段）、业务动作和插槽内容。
- 然后**必须**在页面登记表 `PAGE_MAP` 里加一条。它是「后端菜单组件路径 → 前端页面 + 取数方式」的唯一对照表，位置：`scaffold-vue/src/composables/auth.ts` 第 64 行。
- PAGE_MAP 的真实结构（条目类型 `PageEntry`，定义在同文件第 41-56 行）：key 是后端 `sys_menu.component` 的值（如 `biz/customer/index`）；值是一个对象，可含——
  - `view`：页面组件，懒加载写法 `() => import('@/views/biz/Customers.vue')`；
  - `list`：列表取数函数（配了才会在页面挂载时自动取数）；
  - `exportData` + `exportName`：导出函数与导出文件名（**配了才会显示导出按钮**）；
  - `tree` + `treeList`：树型页面用（不分页、一次全量）；
  - `pageSize`：每页条数，不填默认 10。
- 参照写法：同文件第 94-99 行（`system/post/index` 岗位页的登记）。
- 注意：不在 PAGE_MAP 登记的页面，即使菜单配了也打不开——`sys_menu.component` 必须与 PAGE_MAP 的 key 完全一致。

### 第 7 步：菜单与权限 SQL

- 再写一个版本 SQL（如 `V4__biz_menu.sql`）：往 `sys_menu` 表插一条 `menu` 类型记录（含 `path` 路由、`component` 组件路径＝`biz/customer/index`、`permission` 权限码＝`biz:customer:list`），以及若干 `btn` 类型按钮权限（add / edit / remove）。
- 范例：`scaffold-system/sql/V2__seed_data.sql` 第 67-70 行（岗位菜单 105 + 按钮 1051-1053 的插法）。

### 第 8 步：角色授权

- 登录后台 → 角色管理 → 给需要的角色勾选新菜单和按钮；数据范围在同页选择。超级管理员（admin）无需授权自动可见全部。
- 授权存在 `sys_role_menu` 表（角色-菜单关联表）；读取链路见 01 文档第三节。

### 第 9 步：验证清单

- [ ] 重启后端（开发模式改码自动重启），退出重登（菜单和权限在登录时才加载）
- [ ] admin 能看到「客户管理」菜单，增删改查全部可用
- [ ] 低权限账号：菜单不可见；用工具直接调接口应返回 403（后端真拦截，不只是藏按钮）
- [ ] 「仅本人」数据范围的账号只看到自己的客户（列表与导出同一口径）
- [ ] 查询、重置、分页、导出都正常，导出内容与列表一致
- [ ] 表单校验与重名拦截生效
- [ ] 操作日志页能看到新模块的记录，敏感字段已打码
- [ ] 同步 `PROJECT_MAP.md`（模块地图、API 索引）与 `changelog.md`

> 省力选项：第 2-4 步可先用「系统工具 → 代码生成」导入 `biz_customer` 表生成骨架，再人工补业务逻辑（生成器输出的是开发骨架，不会自动写入工程）。

## 五、避坑清单（体检结论转成的开发守则）

1. **数据权限必须显式接**：新业务的列表/导出，Service 方法加 `@DataScope`、Mapper SQL 显式拼范围条件——不接就是「全部可见」（第二节结论 2）。
2. **权限码前后端同一套**：Controller 的 `@RequiresPermission`、菜单按钮的 `permission` 字段、前端 `PermissionButton` 用同一个码（如 `biz:customer:remove`），拼错一个字母权限就形同虚设。
3. **列表必须数据库分页**：照抄「COUNT + LIMIT」两条 SQL 的既有模式，禁止全查出来在内存里截一段（04 文档守则 2）。
4. **禁止在循环里逐条查库/插库**：批量插入用一条多行 SQL，批量查询用 `IN` 一次取回；现有代码「给角色勾 50 个菜单＝50 条独立 INSERT」就是要避免的写法（04 文档 4.2 节）。
5. **新表必建索引，且关联表两个方向都建**：凡会被 WHERE / ORDER BY / JOIN 用到的列都建索引；`sys_user_role` 缺 role_id 索引就是教训（第二节结论 5）。
6. **导出走统一导出，别自造**：前端在 PAGE_MAP 里配 `exportData`/`exportName` 即自动出现导出按钮；后端沿用「最多 5000 条」的上限约定，预期超 5000 行的业务改流式导出，别把全表装进内存。
7. **页面必须复用 ListPage，别自己拼表格**：查询、重置、分页、导出、勾选、防错乱全部由 ListPage + useListPage 包办，自拼页面等于放弃这些保障，也破坏全站一致性（AGENTS.md 前端准则）。
8. **新页面必须先登记 PAGE_MAP**：`sys_menu.component` 与 PAGE_MAP 的 key 不一致，菜单就打不开页面；不配 `exportData` 就没有导出按钮。
9. **动效统一走 motion.ts**：不许在页面里自起 `requestAnimationFrame` 或引第三方动画库；组件里的定时器（setInterval/setTimeout）和事件监听必须在卸载时清理，照抄现有组件的成对写法（04 文档守则 6、7）。
10. **树型页别照抄全量加载**：`tree: true` 意味着「一次拉全部」，业务树预期超 500 个节点时，先按 04 文档守则 8 分页或分批，别等卡了再改。

## 六、「热铁盒」映射预留

> 本节是占位。等你提供「热铁盒」的业务功能清单后，按第四节流程把每个功能落位成下表的一行，再逐行开工。先映射后动工的价值：把「每个功能用什么页面形态、建什么表、复用什么」想清楚，避免写到一半发现表设计不支撑。

| 业务功能 | 建议页面形态（列表/看板/树） | 需要的表 | 复用哪些组件 | 权限码建议 |
| --- | --- | --- | --- | --- |

|  |  |  |  |  |
|  |  |  |  |  |

填表口径：

- **页面形态**：一行行记录选「列表」；要拖拽改状态、按维度分列选「看板」（ListPage 的 altView 机制支持，见 02 文档第四节）；上下级关系选「树」。
- **需要的表**：主表 + 字典（选项类字段）+ 关联中间表（多对多关系时）；关联表记得两个方向都建索引（避坑 5）。
- **权限码建议**：沿用现有 `模块:资源:动作` 三段式（如 `system:user:list`），新业务建议以 `biz:资源:动作` 开头，与系统模块区分开。
