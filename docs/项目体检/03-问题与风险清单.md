## 一、体检总结论

**这套底座整体是能用的、而且底子不错**：前后端分工清晰、公共能力统一收口，前端流畅度和内存管理达到精心调校的水准，17 条问题里没有一条是"系统跑不起来"级别的事故。**但"高"级的那 1 条（验证码答案明文摆在登录页上）和"中"级里的 3 条（数据权限默认全放行、权限校验无缓存、批量操作失败不刷新）建议在二次开发开始前先修掉**——它们要么是安全地基上的洞，要么是并发和日常使用中最先被踩中的坑，趁现在业务还没长上去修，代价最小。其余 13 条属于"现在无感、数据量或并发上来后逐渐变疼"的记录在案项，可以按节奏排期。

## 二、必读阅读法

1. **先看"高"，再看"中"，"中低"和"低"按节奏排期。** 分级含义：
   - **高** = 安全或正确性上的实洞，建议立即处理；
   - **中** = 现在就能被踩到，或并发/数据量上来后最先被放大，二次开发前建议处理；
   - **中低** = 当前使用无感，是"将来"的问题（与数据量、并发挂钩）；
   - **低** = 小瑕疵、口径不一致或预留未完成的功能，不影响当下使用。
2. **每条问题固定五项**：编号与严重程度 → 什么问题（大白话）→ 现场位置（文件路径：行号，可直接打开对照）→ 对使用的影响 → 改进方向（只给方向，不给代码）。
3. **不必按顺序通读**。急着做决策就只读「一、体检总结论」「五、分级统计与建议处理名单」；想动手修哪条，再回来细读对应条目和「四、好消息」确认哪些地方**不要**动。

> 名词约定：下文出现的**索引**（数据库里给某列建的"目录"）、**缓存**（把问过一次的答案记在手边，下次直接用）、**软删除**（数据不真删，只打个"已删除"标记）、**全表扫描**（数据库没有目录可用，只能一行行翻）等术语，均沿用 01/04 文档的解释口径。

## 三、问题清单

### 3.1 架构与安全（5 条）

#### 1.【高】验证码的"答案"明文摆在登录页上

- **什么问题**：验证码（登录时要求输入的一串字符，用来证明"操作的是人而不是机器程序"）本该只让"看图识答案"。但现在的做法是后端把答案原文直接随接口发回浏览器，登录页再把它当作"图片内容"显示出来。机器人程序只要发一次请求就能读到答案，这道防线形同虚设。
- **现场位置**：`scaffold-system/scaffold-framework/src/main/java/com/scaffold/framework/security/CaptchaService.java:31-35`（把答案放进返回结果）；`scaffold-vue/src/views/Login.vue:102-103`（收到答案存起来）与 `Login.vue:280-283`（把答案逐字渲染在登录页上）。
- **对使用的影响**：任何脚本都能绕过验证码无限次尝试登录。配合弱密码仍有被撞库（拿别处泄露的账号密码批量尝试登录）的风险；系统的登录防线实际只剩"账号密码"一道。
- **改进方向**：后端不再返回明文答案，改为返回服务端画好的图片（答案只留在服务端参与比对）。

#### 2.【中】数据权限的默认值是"全部可见"——漏写一道开关就等于不设防

- **什么问题**：数据权限（不同人登录后只能看到自己该看的那部分数据，比如部门主管只看本部门）。系统约定：业务代码要在方法上贴一个"数据范围"开关才会生效。问题在于——**如果开发的人忘了贴这个开关，系统的默认行为是"所有人可见全部数据"**，而不是"先不给看"。安全设计上这叫"出错时敞开"（fail-open），正确姿势应是"出错时关死"（fail-closed）。
- **现场位置**：`scaffold-system/scaffold-framework/src/main/java/com/scaffold/framework/datascope/DataScopeContext.java:14-17`（查不到数据范围时默认返回"全部"）。
- **对使用的影响**：将来新增业务模块时，开发者漏贴开关不会报错、不会有提示，页面照常能跑——只是所有人都能看到全部数据。这类漏洞上线后很难被肉眼发现。
- **改进方向**：把默认值从"全部可见"改为"仅本人"，漏配时宁可少显示也不多显示。

#### 3.【中】每次判断"你有没有权限"都重新查数据库，从不记答案（合并条目：架构路 + 性能路）

- **什么问题**：用户每点一次受保护的页面/按钮，后端都要实时查数据库 2-3 次（查这个人在不在、查他的角色、查他的权限码），**从不缓存**。放大点：用户管理页的"引导接口"一次要判断 4 个权限，最坏累计约 12 条数据库查询；权限图谱接口还要再来一轮。
- **现场位置**：`scaffold-system/scaffold-system/src/main/java/com/scaffold/system/service/SystemPermissionResolver.java:19-28`（每次实时三连查）；`scaffold-system/scaffold-system/src/main/java/com/scaffold/system/service/SystemManagementService.java:50-53`（引导接口连判 4 次权限）。
- **对使用的影响**：现在单机使用完全无感；一旦多人同时使用，每个请求都被这几次额外查询拖慢，这是并发上来后**最先被放大**的开销。
- **改进方向**：给"用户 → 权限码"加 60 秒级短缓存，角色或菜单变更时主动清掉；只需改权限解析器一处，业务代码不用动。

#### 4.【中低】操作日志是"当场手写完才返回"，写日志失败还会把干成的事变成报错（合并条目：架构路 + 性能路）

- **什么问题**：日志只是"旁路记事本"，但现在每次新增/修改数据，系统都要在同一个线程里**当场把日记写进数据库才响应用户**（33 个写接口都如此）。更要紧的是：如果写日记这一步失败（比如数据库抖动），**已经成功完成的业务操作会被当成失败报错**——数据其实改了，用户却看到"操作失败"。
- **现场位置**：`scaffold-system/scaffold-framework/src/main/java/com/scaffold/framework/audit/OperationLogAspect.java:33-44`（业务成功后当场记日志，记录抛错会连累整体返回）；`scaffold-system/scaffold-system/src/main/java/com/scaffold/system/service/JdbcOperationLogRecorder.java:18-37`（同步写入数据库）。
- **对使用的影响**：平时每个写操作多背一次数据库写入（本地无感，数据库变远变慢后每个操作都变慢）；数据库异常时会出现"明明改成功了却报错"的诡异现象，排查起来非常坑。
- **改进方向**：把日志写入挪到独立线程异步落库，并保证日志失败绝不影响业务请求的返回结果。

#### 5.【低】登录日志预留了"从哪来"的字段，但从来没填过

- **什么问题**：登录日志表建表时预留了 IP 地址、登录地点、浏览器、操作系统四个字段，目的是事后能追溯"这个账号是从哪台电脑登录的"。但代码写日志时只填了账号、成败、提示语、时间，这四个字段**一直是空的**。
- **现场位置**：`scaffold-system/scaffold-system/src/main/java/com/scaffold/system/service/AuthService.java:45/49/54`（写日志时只传账号、成败、提示语）；建表字段见 `scaffold-system/sql/V1__init_schema.sql:188-201`；写入语句见 `scaffold-system/scaffold-system/src/main/java/com/scaffold/system/mapper/AuthMapper.java:81-85`。
- **对使用的影响**：账号被盗或出现异常登录时，无法回答"从哪个 IP、什么设备登进来的"——审计追溯链条断了一截。
- **改进方向**：登录时把请求来源的 IP 和浏览器/操作系统信息解析出来，写进已预留的字段。

### 3.2 性能与流畅度（4 条）

#### 6.【中】"用户-角色"对照表少了一本目录，角色页每显示一行都要把对照表翻一遍

- **什么问题**：`sys_user_role` 这张"谁拥有哪个角色"的对照表，只建了按"用户"方向查的联合主键，**没有给"角色"方向建索引（目录）**。而角色列表每显示一行都要按"角色"方向数一遍"这个角色下有几个用户"——没有目录就只能整表逐行翻。权限关系图接口一次最多拉 5000 个角色，等于把这个翻表动作放大到**最多 5000 次**。
- **现场位置**：建表只有联合主键——`scaffold-system/sql/V1__init_schema.sql:96-100`；每行触发的翻表子查询——`scaffold-system/scaffold-system/src/main/java/com/scaffold/system/mapper/SystemManagementMapper.java:154`；放大点（一次拉 5000 角色）——`scaffold-system/scaffold-system/src/main/java/com/scaffold/system/service/SystemManagementService.java:118`；同方向查询还有 `SystemManagementMapper.java:610-616`。
- **对使用的影响**：当前种子数据几十条完全无感；用户-角色关联过千后，角色管理页和权限图谱页会明显变慢。
- **改进方向**：给 `sys_user_role` 表补一个按"角色"方向的索引（属数据库变更，动手前按项目规则先查表结构确认）。

#### 7.【中低】菜单、部门页不分页一次全拉，表格也没有"只画看得见的行"的能力

- **什么问题**：树型页面（菜单管理、部门管理）不走分页，**一次把全部节点拉到浏览器**；而表格组件渲染时是把传入的每一行都画出来，没有"虚拟滚动"（只渲染屏幕看得见的那几十行，滚到哪画到哪）的机制。节点数长到几千时，页面会明显卡顿。
- **现场位置**：`scaffold-vue/src/composables/list.ts:256-266`（树型页把每页条数设成"无限大"一次拉全量）；`scaffold-vue/src/components/ui/DataTable.vue:145-172`（把全部行依次渲染，无窗口化）。
- **对使用的影响**：当前种子数据几十条完全无感；菜单/部门长到数千条后打开这两个页面会卡。属于"将来"的问题。
- **改进方向**：树表预期超过 500 行前，给表格组件补虚拟滚动，或把树型接口改成分批加载。

#### 8.【低】日志页搜关键词是从头到尾翻整张表，而且是翻两遍

- **什么问题**：日志搜索用的是"内容里包含关键词"的模糊匹配写法（LIKE '%关键词%'），这种写法数据库只能整表逐行比对，**任何索引都帮不上**；操作日志还包含一个能装很长文本的大字段，搜一次等于把大字段也逐条读一遍；而且"数总数"和"取当前页"各执行一遍同样的搜索，**等于全表翻两遍**。用户搜索同理。
- **现场位置**：`scaffold-system/scaffold-system/src/main/java/com/scaffold/system/mapper/SystemManagementMapper.java:344-355`（计数侧，5 个字段含大字段）与 `SystemManagementMapper.java:372-381`（取数侧同样条件再来一遍）；用户搜索见 `SystemManagementMapper.java:24-27`。
- **对使用的影响**：日志几万条之内无感；几十万条后搜索会从毫秒级涨到秒级。
- **改进方向**：日志关键词只搜带索引的少数几个字段；数据量大之后再引入全文索引。

#### 9.【低】保存时的批量关联是"勾 50 个就写 50 条"，一条条来

- **什么问题**：给用户分配角色、给角色勾菜单时，系统是把每个勾选项**逐条**写进数据库——勾 50 个菜单就是 50 条独立的写入语句，而不是一条语句打包写入。
- **现场位置**：`scaffold-system/scaffold-system/src/main/java/com/scaffold/system/service/SystemManagementService.java:767`（用户-角色）、`:774`（用户-岗位）、`:781`（角色-菜单），三处均为逐条循环写入。
- **对使用的影响**：每次保存多花几十毫秒级，给角色分配大量菜单时最明显；平时基本无感。
- **改进方向**：改成"一条语句插入多行"的批量写法。

### 3.3 界面与交互（4 条）

#### 10.【中】用户页批量启用/停用/删除是"一条条同时发请求"，部分失败时界面停在旧数据上

- **什么问题**：用户页勾选多条后点"启用 / 停用 / 删除"，系统是**同时发出 N 条单条请求**（而不是一次批量请求）。只要其中有任何一条失败，系统只弹一个错误提示——**不刷新列表、不清空勾选**，界面上还停留着旧数据，用户分不清哪些成功了、哪些没成功。
- **现场位置**：`scaffold-vue/src/views/system/Users.vue:266-286`（批量状态与批量删除均为逐条并发请求；失败分支只弹提示）。
- **对使用的影响**：这是后台日常操作直接踩得到的体验问题：批量操作出错后，看到的数字和勾选状态都不可信，容易造成误操作（比如以为没删掉又删一遍，或以为删掉了其实还在）。
- **改进方向**：改为后端批量接口一次提交；或前端改成逐条执行、逐条记录结果，最后统一刷新列表并清空勾选。

#### 11.【低】字典"样本册"一次最多显示 100 个字典类型，超出的不显示也不提示

- **什么问题**：字典管理页的"样本册"视图要一次拉取全部字典类型，前端请求了 200 个，但后端对所有列表接口统一**封顶每页 100 条**——所以实际最多只能显示 100 个类型，第 101 个开始**不显示、也没有任何"没显示全"的提示**。（核实修正：原始汇报写"最多 200 条"，实际生效上限是后端封顶的 100 条。）
- **现场位置**：`scaffold-vue/src/views/system/Dict.vue:47`（前端一次请求 200）；封顶逻辑在 `scaffold-system/scaffold-common/src/main/java/com/scaffold/common/domain/PageQuery.java:15,21-26`（每页上限 100）经 `scaffold-system/scaffold-system/src/main/java/com/scaffold/system/service/SystemManagementService.java:202-205,692-697` 生效。
- **对使用的影响**：字典类型少于 100 个时一切正常；超过后样本册会"悄悄少几个"，用户以为那就是全部。
- **改进方向**：超过上限时在界面上明示"仅显示前 N 个类型"，或改为分批加载。

#### 12.【低】字典表格里点"字典名称"链接不看权限，和旁边"字典数据"按钮的口径不一致

- **什么问题**：字典页表格里的"字典名称"是个链接，点开就打开字典数据抽屉——但这个链接**没做权限判断**；而同一行操作列里的"字典数据"按钮是带权限判断的（没权限的人整个按钮都不出现）。同一个功能，两个入口两套口径。
- **现场位置**：`scaffold-vue/src/views/system/Dict.vue:228`（名称链接为普通按钮，无权限判断）对比 `Dict.vue:236`（"字典数据"按钮带 `system:dict:list` 权限码）。
- **对使用的影响**：没有"查看字典数据"权限的用户仍会看到一个能点开抽屉的入口（打开后取数会被后端拦下报错），体验矛盾、口径混乱；后端数据本身不会泄露。
- **改进方向**：给名称链接套上与行内按钮相同的权限判断，统一口径。

#### 13.【低】顶栏判断"是不是苹果电脑"用的是浏览器已废弃的老接口

- **什么问题**：顶栏显示快捷键前缀（Mac 显示 ⌘、Windows 显示 Ctrl）时，判断系统类型用的是 `navigator.platform`——这个浏览器接口已被官方标记为**废弃**（未来版本可能移除、部分新浏览器返回值不可靠），有更现代的替代接口。
- **现场位置**：`scaffold-vue/src/components/layout/Topbar.vue:26`。
- **对使用的影响**：当下仍能工作；将来浏览器移除该接口后，判断会失效，快捷键前缀可能显示错。
- **改进方向**：换成现代的用户代理数据接口或解析用户代理字符串。

### 3.4 数据与存储（4 条）

#### 14.【低】导出写死最多 5000 行，超出的悄悄丢掉

- **什么问题**：所有列表的导出功能一次最多取 5000 条数据生成文件，第 5001 条起**直接不包含在文件里，界面上也没有任何提示**。（核实修正：行号为 84，原始汇报写 85，实质一致。）
- **现场位置**：`scaffold-system/scaffold-system/src/main/java/com/scaffold/system/service/SystemManagementService.java:84`（用户导出取 0-5000 条）；其他导出同模式（如字典导出 `SystemManagementService.java:209`）。
- **对使用的影响**：数据量超过 5000 条时，导出的表格"看起来导出了，其实不完整"，用于对账、汇报时可能出错且难以察觉。
- **改进方向**：超过上限时明确提示"仅导出前 5000 条"；数据量再大后改为流式写出的导出方式。

#### 15.【低】"按哪个字段排序"这个参数从头到尾没人接，是个摆设（核实修正条目）

- **什么问题**：后端统一分页参数里预留了"排序字段、排序方向"两个参数，但**所有列表 SQL 的排序都是写死的**，这两个参数从未被任何查询使用；进一步核实发现，**前端也从未发送过这两个参数**——它是前后端两头都没接线的预留字段。（核实修正：原始描述"传了不生效"，实际是"传不传都一样"，因为前端根本不传。）
- **现场位置**：`scaffold-system/scaffold-common/src/main/java/com/scaffold/common/domain/PageQuery.java:8-11`（参数预留处）；全后端检索仅本文件及其单元测试出现 `sortField`，任何 SQL 均未使用。
- **对使用的影响**：当下无影响（没人用它）；风险在二次开发——后来者以为"传排序参数就能排序"，接上线才发现不生效，白折腾一轮。
- **改进方向**：要么把排序参数接到各列表 SQL 的"白名单排序"里真正实现，要么删掉这两个参数避免误导。

#### 16.【低】菜单是"真删"，其他表都是"打标记假删"；新菜单的编号还是现场算出来的

- **什么问题**：两个小毛病叠加在同一张菜单表上。其一：用户、角色、部门等表删除时都只是打"已删除"标记（软删除，可恢复、可审计），**唯独菜单表是真删**（数据直接消失）。其二：新增菜单时，编号（主键 ID）不是让数据库自动分配，而是"先查一下当前最大编号是多少、再加 1"现场算出来——两个人同时新增菜单时，可能算出同一个编号，**撞车报错**。
- **现场位置**：`scaffold-system/scaffold-system/src/main/java/com/scaffold/system/mapper/SystemManagementMapper.java:660-661`（编号 = 当前最大值 + 1）；`:686-687`（菜单物理删除）；对比部门的软删除写法 `SystemManagementMapper.java:647-652`。
- **对使用的影响**：菜单误删后无法像其他数据一样恢复；并发新增菜单时偶发"保存失败"报错，且越是多人维护菜单越容易触发。
- **改进方向**：新菜单编号改用数据库自增分配；删除方式与其他表统一为软删除（或在文档中明确说明菜单表豁免的理由）。

#### 17.【低】导出的表格文件不防"表格炸弹"——以特定符号开头的内容会被 Excel 当公式执行

- **什么问题**：生成 CSV 导出文件（一种用逗号分隔的纯文本表格格式）时，只处理了逗号、引号、换行这些格式问题，**没有处理"表格炸弹"（公式注入）**：如果某个字段的值以 `=`、`+`、`-`、`@` 开头（比如用户把自己的昵称改成 `=HYPERLINK(...)`），用 Excel 打开导出文件时，这个单元格会被当作公式**执行**。这是数据被人借道导出文件搞事的经典入口。
- **现场位置**：`scaffold-system/scaffold-system/src/main/java/com/scaffold/system/service/SystemManagementService.java:840-849`（单元格转义逻辑，无公式防护）。
- **对使用的影响**：恶意用户可以把危险内容藏在自己能控制的字段（昵称、备注等）里，管理员导出并打开文件时被触发。本地自用风险低，交付给真实业务后属于应修的安全卫生项。
- **改进方向**：对以 `=`、`+`、`-`、`@` 开头的单元格内容前置一个安全符号（如单引号）再写入。
