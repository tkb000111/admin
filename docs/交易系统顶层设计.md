# 交易系统顶层设计（讨论稿）

> 状态：讨论中，未定稿。本文档沉淀 2026-10-13 对话中的顶层分析，供后续讨论修改。
> 核心思想：**不按行业建模，不先建菜单、房间、商品、货架；先抽象「交易」本身，行业只是给交易挂载不同的资源与流程插件。**

## 一、核心模型：交易五要素

任何一门生意，最终都能还原成一张**交易单**。交易单回答五个问题：

| 要素 | 回答 | 举例（餐饮视角） |
|---|---|---|
| 时间 | 何时 | 点单时间、履约（上菜）时间、结账时间 |
| 空间 | 何地 | 桌台、包间 |
| 交易对象 | 谁 | 客户、员工、供应商；**含来源：介绍人、渠道** |
| 资源 | 卖什么 | 菜品、原料、商品、服务、工时 |
| 货币 | 多少钱 | 价格、优惠、支付、账期 |

要点：

- **交易单是系统唯一核心单据**，点单、加菜、结账、退货都是它状态机上的节点。
- 交易明细：交易单里每行 = 一种资源 × 数量 × 单价。
- 资源带「类型」：菜品 / 原料 / 商品 / 服务；菜品挂**配方**（一份菜 = 哪几种原料各多少），结账时按配方自动扣原料库存。
- 空间带「类型」和「状态」（空闲 / 已开台 / 待清台），每个桌台生成二维码，即顾客自助点单入口。
- 交易对象含**来源**（介绍人 + 渠道）：客户档案与每张交易单都记录，后续才能算「哪个渠道带客多、给谁分介绍费」。

要素 → 板块的生长关系：

- 时间 → **数据中心**：报表按时间轴看经营
- 空间 → **顾客手机端**：台码二维码就是顾客入口
- 交易对象 → **营销中心**：会员、储值、渠道带客
- 资源 → **库存中心**：资源的进、耗、存
- 货币 → **财务中心**：钱的流水汇总成账

落到项目里，一级导航候选：交易、资源、空间、对象、营销、库存、财务、数据；现有系统管理类导航保持不变。

## 三、行业差异 = 同一骨架换插件

| 五要素 | 餐饮 | 零售 | 批发 | 服务业（美业/酒店） |
|---|---|---|---|---|
| 空间 | 桌台、包间 | 门店、货架 | 仓库、档口 | 房间、工位 |
| 资源 | 菜品+原料配方 | 标品（条码） | 商品+客户分级价 | 服务项目+技师工时 |
| 对象 | 食客、服务员 | 顾客、收银员 | 经销商（分级） | 预约客户、技师 |
| 流程插件 | 后厨分单、叫号 | 收银台、称重 | 报价、账期、配送 | 预约、排班 |
| 货币 | 即时结账 | 即时支付 | 账期赊销 | 储值卡、次卡 |

**餐饮五要素最全**（空间占用 + 配方扣料 + 服务人员 + C端自助点单）。餐饮做透后，零售、批发约等于减配，不是重做。

## 四、已确认的方向（2026-10-13）

1. **首个验证行业：餐饮**。理由：五要素最全，做透它即可覆盖其他行业的主体能力。
2. **使用范围：单商户**。即一家店自己用系统，「给别人用」指顾客能扫码点单；暂不做多商户平台，但架构上保留将来扩展的可能。
3. 一期 = 后台管理 + **顾客手机端**（手机页面，与后台共用同一套接口）。

## 五、分期建议（讨论中）

| 期 | 内容 | 目的 |
|---|---|---|
| 一期（骨架验证） | 菜品/原料/配方、桌台+二维码、顾客扫码点单、后厨看单、收银结账、按配方自动扣料、当日营业报表；客户档案与交易单留好「来源渠道、介绍人」字段 | 最小闭环：顾客进门扫码 → 吃完结账 → 自动扣库存 |
| 二期 | 采购入库、供应商、盘点、会员/储值/优惠券、渠道带客统计、介绍分佣 | 补齐「进」和「存」，加留客能力 |
| 三期 | 应收应付、对账、成本毛利分析、经营看板 | 财务深化 |
| 远期 | 拿零售场景验证骨架通用性（资源换标品、空间换货架、流程换收银台） | 证明「不按行业建模」成立 |
