## 一、现状调研结论（现在是怎么运作的）

| # | 现状 | 现场位置 | 对这次改造的意义 |
| --- | --- | --- | --- |
| 1 | 菜单存在数据库 `sys_menu` 表，本身就是**任意层级的树**：`dir` 目录 / `menu` 页面 / `btn` 按钮，靠 `parent_id` 父子关系挂接；接口 `/api/auth/routes` 按树原样吐给前端 | `scaffold-system/sql/V1__init_schema.sql` 第 76-95 行；`scaffold-system/scaffold-system/src/main/java/com/scaffold/system/service/AuthService.java` 第 82-129 行（树组装对层级数无硬编码） | **加一级「功能」不用改后端树逻辑**，只需重组种子数据和前端解读 |
| 2 | 前端把这棵树**只按两级解读**：顶级目录 → 侧栏分组标题，子页面 → 可点项。这就是现状的「单轨平铺分组」 | `scaffold-vue/src/composables/auth.ts` 第 151-164 行（buildNav） | 新导航主要是**重写这个解读函数**，而不是动数据链路 |
| 3 | 页面切换是**销毁重建**：路由出口用 `:key="route.path"` 强制每次重新挂载，全项目**没有任何 keep-alive（页面缓存）**，切走再切回，查询结果、表单内容全部丢失 | `scaffold-vue/src/components/layout/AppShell.vue` 第 93-97 行；全 src 无 keep-alive 匹配 | 标签缓存行必须**新建**：标签数据 + keep-alive 缓存名单，是本次工作量最大的一块 |
| 4 | 路由是**扁平注册**：所有页面平挂在根外壳下（`/system/user`、`/monitor/operlog`…），页面的「属于哪个分组」只存在路由元信息的 `group` 字段里，地址本身不体现层级 | `scaffold-vue/src/router/index.ts` 第 53 行；`scaffold-vue/src/composables/auth.ts` 第 166-180 行 | **导航层级可以只改菜单数据，不改路由地址**——旧链接、收藏、菜单 SQL、代码生成模板全部不受牵连（见决策 2） |
| 5 | 移动端现状是**抽屉**：窄于 820px 时侧栏滑出、遮罩点击关闭 | `scaffold-vue/src/components/layout/AppShell.vue` 第 31-32、83 行 | 草案要求**独立视图整页切换**，抽屉逻辑整体拆除 |
| 6 | 顶栏面包屑读的是路由元信息 `group`（分组名）+ `title`（页名）；命令面板读的是 `navGroups`（两级导航数据） | `scaffold-vue/src/components/layout/Topbar.vue` 第 24-25、77 行；`scaffold-vue/src/components/layout/CommandPalette.vue` 第 49 行 | 导航变三级后，这两处是**连带小改**，不是重构 |
| 7 | 权限、数据范围、PAGE_MAP 页面登记表、导出、预取等公共能力**都长在页面层和请求层，不长在外壳层** | `scaffold-vue/src/composables/auth.ts` 第 64-128 行 | 换外壳**不碰**这些能力，10 个页面文件预计一行都不用改 |

**一句话总结**：这次改造 = 后端只重组一次菜单种子数据；前端重写「导航解读」+ 新建「标签缓存」+ 重排「外壳布局」+ 拆「抽屉」；10 个业务页面零改动。

## 二、目标骨架（做成什么样）

### 桌面端（宽屏）

```
┌──────────┬────────────┬──────────────────────────────────┐
│ 功能列    │ 模块列      │  顶栏：面包屑(功能/模块) ⌘K 头像   │
│ (主·深)   │ (次·浅)    ├──────────────────────────────────┤
│          │            │  标签缓存行：[工作台×][用户×][角色×] │
│ ▣后台管理 │ 系统管理    ├──────────────────────────────────┤
│ ○热铁盒… │  用户 角色  │                                  │
│          │  菜单 部门  │        内 容 区（缓存切换）        │
│          │ 岗位 字典…  │                                  │
└──────────┴────────────┴──────────────────────────────────┘
```

- 点**功能**（如「后台管理」）= 浏览：只换右边模块列的内容，内容区不动。
- 点**模块**（如「用户」）= 打开：内容区渲染，同时生成/激活对应标签。
- 视觉层级：功能列用更深一档的面板材质，模块列浅一档；选中态沿用现有玻璃令牌（`styles/tokens.css`），不引入新风格。

### 移动端（≤820px，沿用现有断点）

```
┌────────────────────────┐      「导航」视图 = 功能列 + 模块列
│ 顶栏（精简）             │      两列同屏并排，整页切换
├────────────────────────┤      「界面」视图 = 标签行 + 内容区
│ 标签缓存行（与大屏一致）  │      底部栏 4 格：导航｜界面｜空｜空
├────────────────────────┤
│        内 容 区          │
├────────────────────────┤
│  [导航] [界面] [ ] [ ]   │
└────────────────────────┘
```

- 不做抽屉、不做浮层；底部栏为将来全局操作留两个空位。
- 标签行双端同一套代码、同一套样式。

## 三、核心设计决策（调研后的定案建议，待你确认）

### 决策 1：「功能」这一级不加新表、不加新类型，复用现有目录树
`sys_menu` 已支持任意层级。在种子数据顶部插一个 `dir` 类型节点「后台管理」，把现有「系统管理 / 系统监控 / 系统工具」三个目录**整体挪到它下面**；它们的子页面原样不动。将来热铁盒等业务系统 = 在顶级再插一个 `dir` 节点。
**收益**：后端 `/auth/routes` 一行不改；菜单管理页、权限树、`sys_role_menu` 授权、代码生成的菜单 SQL 模板全部沿用。**改动只剩：种子 SQL 重组 + 一段给已建库执行的迁移 SQL。**
**与需求方对齐的核心判断**：本项目现有「模块」的操作方式（菜单表登记 + PAGE_MAP + 权限码）是好的，**缺陷只在没有「功能」这一级**；所以改造不是换成热铁盒的目录扫描机制，而是把现有这套成熟机制**原样向上复用一层**——功能级的登记、授权、显隐，与模块级走完全相同的链路（详见第五节）。

### 决策 2：路由地址保持现状不变
双列导航的层级感来自菜单数据，不需要 URL 体现层级。`/system/user` 等地址原样保留。
**收益**：PAGE_MAP、componentPaths、深链（如 `?trace=user:1`）、回归脚本、菜单种子里的地址**零改动**。

### 决策 3：标签缓存 = 标签数据（新建） + keep-alive（新建）
- 新建 `composables/tabs.ts`：记录已打开标签（路径、标题、所属功能），提供打开 / 切换 / 关闭 / 关闭其他 / 关闭全部 / 刷新。
- 路由出口套 Vue 官方缓存组件 KeepAlive：标签开着 = 页面在缓存里，切走状态不丢；关闭标签 = 踢出缓存。
- 「刷新」= 把该页面踢出缓存再立即放回，等效重新加载。
- 深链兼容点：日志页靠地址参数定位（如泳道跳转），页面实例被缓存后**不会重跑挂载逻辑**，需给这几页补一个「地址参数变了就响应」的监听——涉及文件：`views/monitor/OperLog.vue`、`views/monitor/LoginLog.vue`、`views/Dashboard.vue`（施工时逐一核对）。

### 决策 4：双端一套内容区
标签行 + 内容区是一段代码；只有「导航挂载点」和「底部栏」按 820px 断点切换。移动端导航视图复用桌面双列组件（并排渲染），不另写一套。

### 决策 5：旧骨架直接退役（不做兼容层）
删除：`Sidebar.vue`、抽屉遮罩逻辑（`rail-scrim` / `is-mobile-open`）、侧栏收起状态 `railCollapsed`、侧栏滑块动效 `slideThumb` 在导航里的用法及相关 `.rail-*` / `.nav-*` 样式。
保留：`Topbar`（重排安置）、`CommandPalette`（改数据源）、外观 / 密码弹窗、命令面板动作、全部页面。

### 决策 6：导航注册机制沿用数据库菜单表——已论证，不照搬热铁盒的目录扫描

需求方指示"只参照、不照搬"并要求论证两种方式孰优。已实地核查热铁盒源码后结论如下：

| 对比项 | 热铁盒：扫目录 + module.json | 本项目：sys_menu 菜单表 | 结论 |
| --- | --- | --- | --- |
| 权限粒度 | 授权单位 =（功能域，面）两级粒度（`server/core/schema-base.sql` 第 37 行），**管不到单个模块、管不到按钮** | 任意菜单节点 + 按钮级权限码（`sys_role_menu` + `permission`） | **菜单表胜**——后台管理的立身之本 |
| 管理员自助调整 | 改名/排序/显隐都要改文件、重新发布 | 菜单管理页点一下即生效 | **菜单表胜** |
| 多环境 | 菜单清单随代码走，各环境一致性与代码版本耦合 | 菜单是数据，各环境独立配置 | **菜单表胜** |
| 新增功能登记成本 | 零登记（建目录即注册，构建生成入口表） | 插一条菜单数据 | 热铁盒省一步 |
| 页面代码注册 | 构建期生成 `entries.js` 静态入口表 | 手写 `PAGE_MAP` | **本质等价**：打包器都要求静态可见的入口，谁也逃不掉 |
| 运行机制 | 服务端轮询扫描文件系统、排除目录边界（`server/index.js` 第 76-90 行） | 一条标准数据库查询 | **菜单表胜**（简单可靠） |

需要澄清的关键事实：热铁盒"插入模块本身就有表"（`server/apps/<功能>/schema.sql` 被扫描建表，见 `server/core/db.js` 第 61 行）——那是**业务数据表**（货架、商品存哪），不是**导航注册**；它的导航与授权仍然是"目录 + 面"模型。

**结论**：功能级**必须**沿用数据库菜单表机制。核心理由一条：这个底座的立身之本是权限体系，而"功能"（业务系统入口）恰恰是最需要按角色授权、最需要管理员自助调整的一级——若功能级走目录扫描，等于把最该管的一层排除在权限体系之外，逻辑倒挂。热铁盒的"面"粒度连"角色 A 能看用户管理、不能看菜单管理"都无法表达。目录扫描是它为"单机轻量、免登记"做的取舍，**不是标准后台底座的做法**（若依等主流方案均为数据库菜单表）。

**从热铁盒只借交互规则，不借机制**（详见第五节末尾"参照清单"）。

## 五、功能与模块的接入规范（改造后怎么加东西）

改造完成后，"往基座里加东西"有且只有两种姿势，**走完全相同的登记链路**（菜单表一条数据 + `PAGE_MAP` 一条登记 + 权限码），区别只是插在树的哪一层：

### 方式 A：插入「独立功能」（一个新的业务系统，与后台管理平级）
以将来接入「热铁盒商城」为例：
1. 菜单管理页（或 SQL）插一个**顶级目录**「热铁盒商城」（`dir`，配图标、排序）。
2. 授权给相应角色（`sys_role_menu` 勾这个目录）——没被授权的角色在功能列里**看不到**它。
3. 其下按老流程挂模块：页面菜单（`menu`，地址 + 组件标识 + 按钮权限码）。
4. 前端在 `PAGE_MAP` 登记页面（视图 + 取数 + 导出）——与现状完全一致。
5. 导航功能列、标签缓存、命令面板、权限显隐**自动生效**，外壳代码零改动。

### 方式 B：插入「模块」（挂进某个已有功能）
与现状加页面的流程**一模一样**，一个字不多：
1. 在目标功能的目录下插一条页面菜单（`menu`，地址 + 组件标识 + 按钮权限码）。
2. 授权角色；前端 `PAGE_MAP` 登记。
3. 该功能的模块列自动多出一项。

### 统一原则（这是本次改造立下的规矩）
- **登记链路全层级统一**：功能级 = 模块级 = 同一张表、同一套授权、同一个 PAGE_MAP。不存在"功能要走另一套机制"。
- **外壳永远不认识任何业务**：`FeatureNav` / `TabBar` 只消费 `/auth/routes` 返回的树，里面有没有热铁盒、有几个功能，外壳一概不知。
- **不做的事**：不引入目录扫描、不引入 module.json 说明书、不做"建目录即注册"——论证见决策 6。

### 参照清单（从热铁盒借什么、不借什么）
| 借（交互规则） | 落在计划哪里 | 不借（机制） | 原因 |
| --- | --- | --- | --- |
| 点功能 = 浏览，**不冲掉**已打开的界面 | 二、目标骨架 | 目录扫描 / module.json / 建目录即注册 | 决策 6：权限粒度与管理能力是命根子 |
| 「当前打开的工作」是唯一真相源，浏览位置（browseF）与打开位置（openF）分叉记录、推导选中态 | 阶段二/三 tabs.ts 设计 | 授权按"面" | 本项目按角色 + 按钮级授权，粒度必须保留 |
| 刷新后回到上次位置（本地记忆，带回退：记忆失效 → 显式声明的默认落点 → 第一个） | 决策 3 + 已拍板问题 3/5 | 模块自建 schema.sql 扫描建表 | 本项目建表走迁移 SQL，统一可控 |
| 小屏三格语义：「界面」格 = 当前打开的工作本身，不是清单 | 二、目标骨架（移动端） | 模块 CSS 注入/回收 | Vue 单文件组件样式随分块自带 |
